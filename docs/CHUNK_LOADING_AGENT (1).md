# CHUNK_LOADING_AGENT

## Objective

Optimize chunk loading speed on PocketCraft so players no longer hit blank/unloaded terrain on world join or exploration. This involves four areas: JVM launch flags, Paper config tuning, `server.properties` defaults, and a new UI-level "Fast Start" toggle in Settings.

---

## Context

- **App package:** `com.pocketcraft.server`
- **JVM is launched via native C:** `launcher.c` using `dlopen()`
- **Foreground service:** `ServerHostService.kt`
- **Settings UI:** `SettingsScreen.kt` (Jetpack Compose)
- **Preferences:** `AppPreferences.kt`
- **Console output parsing:** `ServerConsole.kt`
- **Server type:** Paper (primary), with Purpur/Fabric also supported
- **Theme colors:** Background `#0A0A0F`, accent purple `#6C63FF`, green `#3DDC84`, red `#FF4757`, orange `#FFB142`

## Task 1 — JVM Launch Flags (`launcher.c`)

### What to do

Locate the array or string where JVM args are constructed before calling `JNI_CreateJavaVM` or equivalent. Add the following flags if not already present:

```c
"-XX:+UseG1GC",
"-XX:G1HeapRegionSize=8M",
"-XX:+ParallelRefProcEnabled",
"-XX:+UnlockExperimentalVMOptions",
"-XX:+AlwaysPreTouch",
"-XX:+DisableExplicitGC",
"-XX:MaxGCPauseMillis=200",
"-XX:+UseStringDeduplication",
"-Djava.io.tmpdir=/data/data/com.pocketcraft.server/cache",
"-Dfile.encoding=UTF-8",
"-Dusing.aikars.flags=https://mcflags.emc.gs",
```

### Why

- `AlwaysPreTouch` — pre-warms JVM memory pages at startup so there's no stutter when the first chunks generate.
- `G1GC` with `ParallelRefProcEnabled` — reduces GC pause time during chunk I/O bursts.
- `DisableExplicitGC` — prevents Paper plugins from triggering a full GC, which causes freeze spikes.
- `MaxGCPauseMillis=200` — keeps pauses short and consistent.

### Guard condition

Do NOT remove existing RAM allocation flags (`-Xms`, `-Xmx`). These new flags are additive. Append them after the heap size flags.

## Task 2 — Default `server.properties` values

### File location

The agent must locate where PocketCraft writes the initial `server.properties` on world creation. This is likely in `ServerHostService.kt`, `AppPreferences.kt`, or a utility that copies a bundled template from `assets/`.

### Change these defaults

```properties
view-distance=6
simulation-distance=4
network-compression-threshold=256
max-tick-time=60000
```

### Why

- `view-distance=6` (down from default 10) — the single biggest impact on chunk load time. Clients load 169 chunks instead of 441.
- `simulation-distance=4` — entities and redstone only tick close to the player; far chunks still render but don't process.
- `network-compression-threshold=256` — compresses packets above 256 bytes, reducing bandwidth for chunk data on mobile networks.

### Important

If the user has previously set custom view/simulation distances (via RAM mode or manual override), do NOT overwrite them. Only apply these as initial defaults when a new world/server is first created.

## Task 3 — Paper Config (`paper-world-defaults.yml`)

### File location

This file is generated by Paper inside the server's working directory at `world/paper-world-defaults.yml` or the server root. PocketCraft must write or patch this file before the server first starts, OR apply it via a startup config copy from `assets/paper-world-defaults.yml`.

### Recommended approach

Bundle a `paper-world-defaults.yml` template in `assets/` and copy it to the server directory on first launch (if the file doesn't already exist). Contents:

```yaml
_version: 29

chunks:
  auto-save-interval: default
  delay-chunk-unloads-by: 10s
  entity-per-chunk-save-limit:
    arrow: 16
    dragon_fireball: 3
    egg: 8
    ender_pearl: 8
    experience_ball: 8
    fireball: 8
    firework_rocket: 8
    small_fireball: 8
    snowball: 8
    thrown_exp_bottle: 3
  max-auto-save-chunks-per-tick: 8
  prevent-moving-into-unloaded-chunks: true

chunk-loading-basic:
  player-max-chunk-load-rate: 150
  player-max-chunk-send-rate: 75
  target-player-chunk-send-rate: 12

chunk-loading-advanced:
  auto-config-send-distance: true
  player-loading-priority-override: 8
  player-max-concurrent-loads: 20
```

### Key tuning notes

- `player-max-chunk-load-rate: 150` — raised from default 100. Phones with fast I/O can push chunks faster.
- `player-max-chunk-send-rate: 75` — how many chunk packets per second are sent to the client. 75 is safe for mobile.
- `player-loading-priority-override: 8` — biases the chunk loader to prioritize the player's immediate vicinity.
- `prevent-moving-into-unloaded-chunks: true` — stops players from walking into void terrain; they are held until the chunk loads.

## Task 4 — "Fast Start" Toggle in Settings UI

### Files to edit

- `SettingsScreen.kt` — add the toggle card
- `AppPreferences.kt` — add the preference key
- `ServerHostService.kt` — read the preference and apply `view-distance`/`simulation-distance` before server start

### `AppPreferences.kt`

Add a new boolean preference:

```kotlin
var fastStartEnabled: Boolean
    get() = prefs.getBoolean("fast_start_enabled", false)
    set(value) = prefs.edit().putBoolean("fast_start_enabled", value).apply()
```

### `ServerHostService.kt`

Before writing or launching `server.properties`, check this flag:

```kotlin
val viewDistance = if (appPreferences.fastStartEnabled) 5 else 6
val simDistance = if (appPreferences.fastStartEnabled) 3 else 4

// Write to server.properties
serverProperties["view-distance"] = viewDistance.toString()
serverProperties["simulation-distance"] = simDistance.toString()
```

### `SettingsScreen.kt`

Add a settings card in the Performance section (or create one if it doesn't exist). Use the app's existing card/toggle pattern:

```kotlin
SettingsToggleCard(
    title = "Fast Start",
    subtitle = "Lower render distance for faster chunk loading. Best for weaker devices.",
    icon = Icons.Default.FlashOn,
    iconTint = Color(0xFFFFB142), // orange accent
    checked = appPreferences.fastStartEnabled,
    onCheckedChange = { appPreferences.fastStartEnabled = it }
)
```

Display a small info chip below the toggle when enabled:

```kotlin
if (appPreferences.fastStartEnabled) {
    Text(
        text = "View: 5 chunks • Sim: 3 chunks",
        fontSize = 11.sp,
        color = Color(0xFF3DDC84), // green
        modifier = Modifier.padding(start = 16.dp, bottom = 8.dp)
    )
}
```

## Task 5 — Chunky Auto-Run on New World (Optional but Recommended)

### What

Bundle the **Chunky** Paper plugin JAR and auto-run a pre-gen on new world creation so players don't encounter blank terrain around spawn.

### Steps

1. Download `Chunky-Bukkit-X.X.X.jar` from [chunky.pl3x.net](https://chunky.pl3x.net) and place it in `assets/default_plugins/`.
2. On new world creation, copy it to `<server_dir>/plugins/` (same flow as other bundled plugins).
3. After server starts, detect the `Done` log line in `ServerConsole.kt` (server ready signal) and inject this command via the server's stdin:

```kotlin
// In ServerConsole.kt or ServerHostService.kt, after "Done" is detected in logs:
if (isNewWorld && appPreferences.chunkyAutoPregen) {
    sendCommand("chunky world world")
    sendCommand("chunky radius 300")
    sendCommand("chunky start")
}
```

4. Add a preference `chunkyAutoPregen: Boolean` (default `true`) in `AppPreferences.kt`.
5. Parse Chunky's progress output in `ServerConsole.kt` and optionally surface it in the UI as a banner:

```
[Chunky] Progress: 45.2% (x chunks/s)
```

Regex to match:
```kotlin
val chunkyProgressRegex = Regex("""Progress: ([\d.]+)%""")
```

Show a dismissible banner on the Home screen while pre-gen is running:

```kotlin
ChunkyProgressBanner(
    progress = chunkyProgress, // 0f..1f
    visible = isPregenRunning,
    accentColor = Color(0xFF6C63FF)
)
```

## Task 7 — Fix Client Chunk Render Mesh Delay (Wireframe / Transparent Chunks)

### Problem

Players see chunk outlines with transparent/invisible geometry inside — wireframe borders drawn but no blocks rendered. This is a **client render mesh build delay**: the server sends chunk data faster than the client can compile it into geometry. The result looks like floating chunk borders with sky visible through solid terrain.

This is confirmed by the debug screenshot showing:
- Diagonal wireframe trapezoids (chunk border overlay — F3+G)
- Transparent interiors despite block data being present ("Stone — Minecraft" tooltip visible)
- Low FPS spikes (`1% low: 21`, `0.1% low: 20`) indicating render thread stalls

### Root cause

Paper's default chunk send rate floods the client with packets. The client render thread queues them but can't build meshes fast enough, causing the visible delay. The fix is to **slow the send rate** so the client render thread stays ahead of the incoming data.

### Fix 1 — Adaptive chunk send rate in `paper-world-defaults.yml`

Update the existing bundled `assets/paper-world-defaults.yml` template:

```yaml
chunk-loading-basic:
  player-max-chunk-load-rate: 150        # max cap — Paper will stay below this automatically
  player-max-chunk-send-rate: 100        # upper ceiling only — auto-config overrides this per player
  target-player-chunk-send-rate: -1      # -1 = fully automatic, Paper calculates per player ping

chunk-loading-advanced:
  auto-config-send-distance: true        # KEY FLAG — Paper auto-throttles based on player latency
  player-loading-priority-override: 10
  player-max-concurrent-loads: 12
```

**How auto-config works:**
- `auto-config-send-distance: true` tells Paper to measure each player's ping every tick and dynamically adjust how many chunk packets they receive per second
- Low ping (LAN/same WiFi) → up to 100 chunks/sec → chunks render almost instantly
- Medium ping (good mobile) → ~50–60 chunks/sec → smooth render, no wireframes
- High ping (poor connection) → ~20–30 chunks/sec → slower but no queue overflow = still no wireframes
- `target-player-chunk-send-rate: -1` disables the fixed target entirely and lets Paper's adaptive algorithm take full control

**Why this is better than any hardcoded value:** A fixed rate of 40 is too slow for LAN players and too fast for high-latency mobile players. Auto-config gives every player the optimal rate for their exact connection.

Fewer concurrent chunk loads means each individual chunk finishes generation and mesh compilation sooner, reducing the window where chunk borders exist without content.

### Fix 3 — Add `paper-global.yml` chunk system config

Create `assets/paper-global.yml` template and copy to server root on first launch if it doesn't exist:

```yaml
_version: 29

chunk-system:
  gen-parallelism: default       # let Paper auto-tune to available CPU cores
  io-threads: 2                  # dedicate 2 threads to chunk I/O (read/write)
  worker-threads: 2              # dedicate 2 threads to chunk generation
```

On a phone with 4–8 cores, this ensures chunk gen doesn't compete with the main server tick thread.

### Fix 4 — Inject render distance hint on player join

In `ServerHostService.kt` or a bundled startup plugin, inject the following command after a player joins (detect `[Server] player joined the game` in `ServerConsole.kt`):

```kotlin
// After player join detected in logs:
sendCommand("send-chunks $playerName")   // Paper command — forces resend of all chunks in view distance
```

This is a recovery command — if a player loads into a world with blank chunks, this forces a clean resend.

Alternatively, instruct players via an in-game message on first join. Add to a bundled `plugins/PocketCraft/config.yml`:

```yaml
join-message: "§aChunks loading... stand still for 5 seconds for the best experience."
```

### Fix 5 — Disable chunk debug overlay warning in UI

The wireframe lines in the screenshot are the **F3+G chunk border overlay** being left on by players. Add a tip in the PocketCraft Home screen when the server is running:

In `HomeScreen.kt`, show a one-time dismissible card:

```kotlin
InfoCard(
    message = "Tip: Press F3+G in Minecraft to hide chunk border lines.",
    icon = Icons.Default.Info,
    iconTint = Color(0xFF6C63FF),
    dismissible = true,
    preferenceKey = "tip_f3g_dismissed"
)
```

Store dismiss state in `AppPreferences`:

```kotlin
var tipF3GDismissed: Boolean
    get() = prefs.getBoolean("tip_f3g_dismissed", false)
    set(value) = prefs.edit().putBoolean("tip_f3g_dismissed", value).apply()
```
